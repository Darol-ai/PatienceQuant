# 用 Qlib + vnpy 拼一条纵切，不实现愿景文档的完整架构

## 背景

助教下发的《金融量化交易平台产品需求文档》描述的是企业级平台：多市场、OMS/EMS、
高频低延迟层（C++/Rust、邻近部署）、AI 实时编排、多租户 RBAC、Spark、ClickHouse/Doris，
16–27 个月、10 个团队。本项目是课程小组作业，交付窗口 2–3 天，现场演示。

## 决定

只交付一条端到端**纵切**，对齐愿景文档 §19.1 的基本功能验收（①数据→策略→回测→模拟→
"实盘"、②回测可复现、③订单/成交/持仓/资金事件级追踪 + 日终对账、⑤AI 操作留痕）：

- **选股策略**：Qlib（Alpha158 因子 + LightGBM + 滚动回测），只产出信号。
- **交易策略 / 模拟盘**：vnpy `PortfolioStrategy` 消费信号，本地模拟撮合，带订单状态机与对账。
- **数据**：AKShare + BaoStock 免费源 → 本地 DuckDB。
- **前端**：fork `AlphaStock_A`（FastAPI + Vue3 + ECharts）扩展。
- **AI**：DeepSeek/Qwen API 提供策略助手与风险助手，带审计留痕。

## 明确不做（本期）

Rust / 高频层、ClickHouse / Doris / Spark、多市场与港股、多租户 RBAC、策略发布审核流程、
真实券商实盘（仅留适配器接口桩）。这些写入愿景文档的"目标态"，不在 v1。

## 理由

- 2–3 天内不可能实现愿景文档哪怕 P0 子集；纵切能覆盖全部原始作业要求且可演示。
- Qlib 与 vnpy 都是主流大项目，职责边界清晰（Qlib 出信号、vnpy 管执行），
  接缝是"日期 × 股票 → 目标权重"的表，集成成本低，避免自造回测/撮合引擎。
- 数据量小（沪深300 日线 + 近端分钟线），DuckDB 单机足够，省去分布式组件运维。

## 已知代价

- 放弃了"Python + Rust"的技术亮点（愿景文档和早期设想都提到）。若核心提前完成，
  可回补一个 PyO3 因子计算小内核，但不换主引擎。
- vnpy 的股票组合回测文档少于其期货 CTA 用法，集成有踩坑风险；优先级排序已按
  "做不完就从展示层往下砍"处理。
