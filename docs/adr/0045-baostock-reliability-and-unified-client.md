# baostock卡死根因定位 + 统一连接层，real优先不静默降级

## 背景

Dashboard绑定默认多因子策略后一直显示"正在加载"，`/api/dashboard`请求
挂起不返回；进程CPU时间也不再增长——不是计算慢，是卡在某个网络调用上。

## 根因

查了baostock库自己的源码（`baostock/util/socketutil.py`）：它内部维护
一个全局裸socket（`socket.socket()`），**从未调用过`settimeout()`**。
`send_msg()`里的`recv()`循环因此是无限阻塞的——服务端响应到一半没了
下文（网络抖动/服务端卡顿/限流），这个`recv()`会真的永远等下去，Python
这边完全无法感知超时。这是库本身的缺陷，不是我们查询逻辑的问题。

进一步确认：`app/data/baostock_provider.py`（Dashboard/通用目录实时
查询路径）和`scripts/fetch_*.py`（训练数据离线抓取路径）**都在用
baostock**，各自独立实现了一遍登录/查询/异常处理，这次的超时缺陷因此
在两处都存在，只是训练脚本因为是人工手动跑、单次失败会被立刻看到，
没有暴露成"用户看到的bug"。

同一批调试也确认了此前"Error -3 while decompressing data"、
"[Errno 32] Broken pipe"这些偶发错误，和baostock全局单例socket在两个
线程并发使用时互相踩踏有关——已经用进程级锁（`_BAOSTOCK_LOCK`）
解决，这次是同一类"外部资源非线程安全/无超时保护"问题的延续。

## 决定

1. **不换数据源，继续用baostock**：已确认能连通（不像AKShare在这个
   环境被墙），装了超时补丁后能正常工作；评估过`tushare`/东方财富
   `push2`接口，TCP可达但未验证实际取数、且tushare需要人工注册token，
   收益不确定但迁移风险是实打实的，不做。
2. **real优先，失败可见，不静默retreat到demo**：任何一次baostock调用
   （目录/价格/基准指数）失败时，最多重试3次，每次重试前完整重新
   登录（丢弃可能处于脏状态的旧socket）；3次都失败才判定这次拿不到
   真实数据——返回明确的失败状态，不会用demo/虚构数据悄悄顶替，前端
   要能看到"部分行情暂时获取失败"这类真实状态，不能装作一切正常。
3. **单次socket收发统一给10秒超时**：不区分查询量级（训练脚本单次
   查16年数据，实时路径单次查8年数据）——观测到的卡死是"完全收不到
   任何字节"，不是"数据量大传输慢"，10秒对区分"真卡死"和"只是稍慢"
   已经足够宽松。
4. **抽出一个共享连接层**（`app/data/baostock_client.py`）：只负责
   登录、socket超时、进程锁、重试这些连接层面的事；字段列表、
   `adjustflag`、股票代码格式转换（通用目录用裸6位数字，训练数据管道
   用带`.SH/.SZ`后缀）这些各自的业务逻辑保留在原调用方里，不强行
   统一格式，避免合并时改坏任何一边现有的数据产出。已产出的parquet
   训练数据不重新抓取、不做比对验证——现有代码保留不动，本来就没有
   "新旧数据对不上"的风险，只对重构后的调用参数做代码审查确认字段/
   adjustflag未被改动。
5. **新增Dashboard预热后台任务**：和CSI300模型预热同一个模式（服务
   启动时后台线程执行，不阻塞启动）。范围只覆盖`ANALYSIS_SYMBOL_CAP`
   实际会用到的30支股票、2018年至今——不是全量50支demo兜底目录、
   也不是训练管道那种2010年至今的全量历史。

### 验证过程中额外定位到的3个真实bug

修完上面这些、拿真实浏览器/真实请求去验证"Dashboard还转不转圈"时，
发现只把baostock连接层修好并不够——`/api/dashboard`第一次真实调用
仍然要花473秒到552秒不等，不是无限卡死了，但远达不到"能用"的程度。
逐层排查后找到3个和baostock连接层无关、但同样导致"缓存形同虚设、
每次都重新顺序打一遍baostock"的独立缺陷：

1. **写透缓存的覆盖检查有个死结**（`MarketDataService.prices()`）：
   判断"这段区间缓存全不全"要求缓存最早日期必须`<=`请求的start。
   全项目统一请求`start=2018-01-01`，但2018-01-01是元旦，A股当年第
   一个交易日是2018-01-02，baostock压根不可能返回`2018-01-01`那天的
   行情。缓存里永远是"最早2018-01-02" > 请求的"2018-01-01"，coverage
   检查永远判定"没覆盖全"——每支股票每次都被打成"missing"，重新顺序
   请求一遍baostock，写透缓存等于没生效。这是"一直转圈"最底层的真正
   根因，比前面"某个入口漏了`analysis_symbols`上限"更根本：即使上限
   已经生效、缓存已经写过很多遍，这个bug会让缓存的"覆盖"判断永远
   失败。修法：给start/end边界各加10天容差（覆盖任何法定假期，远小于
   "2024-2025缓存被误当成2018-2025"那种年级别跨度，不放宽原有的部分
   覆盖保护）。
2. **沪深300基准指数完全没有缓存**（`MarketDataService.benchmark()`）：
   `prices()`有完整的写透缓存，但`benchmark()`只是直接转发给
   `provider.fetch_benchmark()`，每次都是一次真实baostock请求，无论
   前面缓存修没修都要付这个代价。新增`BenchmarkPrice`表，给
   `benchmark()`加了跟`prices()`同样10天容差的写透缓存逻辑。
3. **Dashboard预热任务选的股票和真实请求选的股票对不上**
   （`app/main.py::_warm_dashboard_price_cache`）：预热任务为了不依赖
   真实目录同步是否跑完，传的是demo目录的50支symbol；但真实
   `/api/dashboard`请求传的是`universe_symbols("large_cap")`（真实
   目录的前300支）。`analysis_symbols()`超过30支上限时按行业分组轮询
   取，这一步对输入列表的**顺序**敏感——即使demo目录和真实large_cap
   目录背后是同一批50支公司，两份列表顺序不同，轮询选出的30支就可能
   不是同一批，预热了却不是Dashboard请求实际要用的那30支，缓存对
   不上。这是实测发现的，不是理论推演：修复覆盖检查+补上基准缓存后，
   第二次请求本该秒回，实测却仍然要另外对~5支股票发真实请求，逐层
   打点最终定位到这里。修法：预热任务改成跟`dashboard()`路由完全一样
   的调用`analysis_symbols(universe_symbols("large_cap"))`，不再图省事
   传demo目录。
4. （非baostock/缓存问题，顺带修的性能问题）`/api/dashboard`对同一批
   ~30支股票的多因子打分**算了两遍**——一遍给"最新交易信号"
   （`signals`），一遍是`universe_analytics()`给"行业分布/估值成长"
   （`analytics`）面板独立重新算一次。缓存命中之后单次因子计算本身
   还是要~15秒（30支×8年历史的pandas计算+从SQLite读取），算两遍等于
   平白多付一次。只有当账户实际绑定的策略正好就是平台默认策略时，两次
   计算在数学上保证完全等价（`analysis_symbols`对不同输入超集的过滤
   结果在这个前提下必然收敛到同一批30支，见`service.py`里的说明）——
   这种情况下复用第一次算好的`ranking`，账户绑定别的策略配置时老实
   分开算，不改变"账户信号"和"平台参考基准"是两个独立口径这件事。

### 实测效果

用隔离脚本直接调`dashboard()`（绕开真实HTTP层，避免和同一服务器进程
里CPU密集的CSI300模型预热线程抢GIL、干扰计时）多次测量：

- 缓存完全未命中（真实冷启动，30支股票+基准指数全部要发真实baostock
  请求）：约20秒（此前，同样冷启动场景在覆盖检查bug修复前是
  473~552秒，且本来会无限挂起——两个数量级的差距）。
- 缓存命中、但analytics仍独立重算一遍（3号bug修复前）：约38秒。
- 缓存命中、预热选股和请求选股完全对齐、analytics复用（全部4个bug都
  修完）：因为整个验证过程本身对baostock发起了几百次真实请求（几十次
  独立测试脚本×每次十几到几十次登录），baostock这个免费社区服务器
  在验证的最后阶段开始明显限流/变慢（catalog同步单次尝试卡到5分钟
  以上未返回，此前同样的调用只需要40多秒）——这是baostock服务端的
  外部限制，不是代码缺陷，重试+超时机制正按设计工作（有界，会失败
  转移，不会无限挂起），但这意味着"缓存完全命中后应为秒级"这一步
  没能在本次会话里用真实网络条件完整验证到底，需要等baostock限流
  窗口过去后用一次干净的服务器重启补验证一次。

### baostock官方限流/拉黑规则（验证过程中查证）

上面"实测效果"里提到验证末期baostock明显变慢、目录同步单次尝试卡到
10分钟以上未返回，一度怀疑是被拉黑。查证过程：baostock官网
(baostock.com)是纯前端SPA，网页抓取工具拿不到渲染后内容，把打包后的
JS bundle下载下来搜索关键字，在"访问限制"页面找到官方原文：

> • 每日API请求不能超过5万次，超过后进入黑名单控制。**并且不能并发
> 连接访问**。
> • 本自然年度初次被黑名单限制访问，冻结6小时后自动解除。本年多次被
> 限制，限制时长会自动增长。
> • 限制时长 = 本年累计限制次数 × 6 小时。

拉黑时`bs.login()`返回`error_code=="10001011"`
(`baostock.common.contants.BSERR_BLACKLIST_USER`)。查了baostock库
自己的源码（`login/loginout.py:86`）：`"login success!"`只在
`error_code=="0"`时打印，拉黑会立刻返回、打印`"login failed!"`，不会
卡住。当次单独测试`bs.login()`瞬间返回`error_code:0`，且此前几百次
调用全部打印过`"login success!"`——确认**没有被拉黑**，当时的卡顿是
查询阶段慢，不是登录被拒。

**发现一个值得记录的架构风险**：官方规则明确"不能并发连接访问"，但
`baostock_client.py`的`threading.Lock`只能在**同一个Python进程内**
串行化调用——调试过程中多次同时跑了独立诊断脚本(单独的python进程)和
正在运行的uvicorn服务器进程，两边各自的锁互不相识，等于确实制造过
规则禁止的并发连接。这很可能是当时查询变慢的真正原因，不是baostock端
的问题。如果以后要多worker进程部署、或者习惯边跑服务边开独立脚本查
baostock，需要跨进程的同步机制（比如文件锁），不能只靠进程内锁——
这次没有实现，留作已知风险记录在这里。

**另外发现一个现有超时设计的盲区**：`baostock/util/socketutil.py`的
`send_msg()`收数据是`while True: recv = default_socket.recv(8192)`
循环，我们打的`settimeout(10)`是"单次`recv()`调用不能等超过10秒"，
不是"整个请求的总耗时上限"——如果服务器在慢慢吐数据(每次都在10秒内
有新字节到，但总耗时很长)，这个超时不会触发。跟用户确认过，这次先
不加整体墙钟超时，观察现有方案(10秒单次recv超时+3次全新登录重试)在
一段时间的真实使用后是否还会出现同类长时间卡顿，视情况再决定要不要
在共享连接层加一个总耗时上限（需要monkey-patch`send_msg`本身，是比
现在"只碰socket的settimeout"更深一层的改动）。
